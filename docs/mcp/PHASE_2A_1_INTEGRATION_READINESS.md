### Confirmed B02 causes and refinement

**Fault A — unconditional bootstrap cleanup (previously corrected, independently reproduced).** An isolated build substituted **only** `getCurrentUser` from Git HEAD into the current frontend, using a Vite loader; the checkout was never reverted. After one real rotation had completed, one tab's fresh bootstrap GET was delayed nine seconds. Its existing eight-second timeout made the historical function call `clearTokens`. The first deletion stack is `getCurrentUser`; the backend family remained ACTIVE/unrevoked with two refresh records, one consumed and exactly one refresh POST. [Serialized negative control](../../backend/checks/phase1-5-0febc84ac8d34d84a7bb66ea315967ba/independent-auth-audit-serialized-bootstrap-control-reload.json), [control provenance](../../backend/checks/phase1-5-0febc84ac8d34d84a7bb66ea315967ba/negative-control-source.json). This expected defect reproduction is not counted as a current-code PASS. Current code preserves those credentials; an unavailable fresh bootstrap grants no context and may show login until a subsequent successful reload.

**Fault B — stale renderer storage at Web Lock handoff (newly verified and corrected).** Another real three-tab control captured the missing failure mechanism: tab 3 stored the healthy successor at timestamp `1794472154931`; tab 2's coordinator cleared both shared keys at `...4932/4933`; tab 2 received the successor storage events only at `...4936/4942`. The first erasure stack was `Object.expire` inside the unchanged coordinator, **before** bootstrap cleanup. There was only one refresh POST, from tab 3, and no marker write/POST from tab 2. The waiting tab therefore rejected the already-attempted predecessor while reading its stale token pair; its local equality guard then erased the globally newer pair. [Real storage/HTTP trace](../../backend/checks/phase1-5-0febc84ac8d34d84a7bb66ea315967ba/independent-auth-audit-negative-control-configured.json).

The earlier nine-second experiment reproduced both possible erasers; it was insufficient to attribute all failures to the bootstrap timeout. The new first-erasure trace establishes a separate coordinator race and explains why the previous patch could still lose healthy credentials. Web Locks serialize cooperating work but must not be treated as a cross-renderer storage-cache receipt. The [HTML storage standard](https://html.spec.whatwg.org/multipage/webstorage.html#the-localstorage-attribute) leaves cross-agent-cluster interaction unspecified; the concrete failure here was observed, not inferred from the standard alone.

The refinement changes the attempted-predecessor decision to wait for the pending **completed two-key credential update**, using actual `storage` events. It verifies the received pair still belongs to the expected session and returns the successor without another POST. An intervening new login/logout wins. If no receipt arrives, the wait ends after **8 seconds** with `RefreshStorageUnavailableError`: the current tab requires sign-in but **does not clear or overwrite the uncertain shared pair**. The interceptor preserves that safe error instead of converting it back to the original Axios 401, which could authorize bootstrap cleanup. A different, newer session is not locally expired by the old error. A consumed credential is never replayed. A receipt resolves as soon as the completed pair is present; this is not a fixed delay before refresh and does **not** raise the existing Axios GET timeout.

An intermediate receipt-timeout implementation still erased the pair after its deadline. A new regression rejected that behavior before the final policy was implemented: [uncertain-state failure](../../backend/checks/phase1-5-0febc84ac8d34d84a7bb66ea315967ba/uncertain-receipt-before.txt). The deadline is now a liveness bound, not an assumption that a stale cache is authoritative. In the issuer-loss case an expired access/spent refresh pair may remain stored until explicit logout or new login; it grants no browser user context, its access request returns 401, and its refresh is not replayed. Backend revocation/absolute-expiry rejection and explicit logout still clear credentials normally. This distinction protects another healthy tab from an uncertain cleanup decision.

Three new coordinator tests failed before this refinement and pass afterward. Four receipt-helper component tests cover an already-present update, incomplete pair/foreign storage event, logout and an actual eight-second missing-receipt deadline/listener cleanup. An additional API component test proves the uncertainty error cannot become a cleanup-triggering bootstrap 401. They use synthetic DOM/storage/transport and are explicitly component evidence. Native browser cases separately use actual password verification, JWT issuance, PostgreSQL/Redis, native Web Locks and real presence.

Issuer reload after the backend consumed a refresh still loses that response safely: no second POST with that predecessor, no credential restoration, and fresh sign-in is required. This is an unavoidable ambiguous-delivery case under the non-replay policy, not a reason to relax reuse detection. A05 executes it and verifies that the retained predecessor cannot authenticate. A06 executes new-login versus old-success races; A07 revokes authority while a successful response is held. Timing interception only delays or releases responses fetched from the real backend; it does not replace identity or authorization.

## B02 investigation and authentication changes

The existing coordinator already serializes cooperating tabs with native Web Locks, shares an in-tab pending promise, records the refresh JTI before dispatch and never retries a refresh POST. PostgreSQL locks and durable reuse revocation remain authoritative. Raising the eight-second bootstrap timeout or accepting reused refresh credentials would not address the verified frontend defect; neither was done.

**Reproduced mechanism:** after access expiry and one successful real rotation, delaying one tab's retried `/auth/me` GET by nine seconds exceeded its unchanged eight-second timeout. The old `getCurrentUser()` catch cleared shared tokens for every read failure. Both tabs consequently reached login while PostgreSQL retained an unrevoked family with two refresh rows, one consumed. Four undelayed baseline B02 runs passed, illustrating why a focused retry alone was insufficient. The controlled baseline failed while waiting for two restored presence sockets. See [baseline delayed failure](../../backend/checks/phase1-5-c58a281c34a74b8080c4bc4f91cf2a76/browser-B02-delayed-before.json).

Changes in `frontend/services/mockApi.ts`:

- Capture the bootstrap session identity; discard success or failure after an account/session/tenant change.
- If credentials advanced within the same session during a failed read, retry **only that GET once**, using the stored successor. No refresh POST retry and no infinite bootstrap loop.
- A transport failure alone preserves credentials; a current-session authentication rejection still expires the session. An unavailable bootstrap does not grant a user context.
- Refresh without native Web Locks fails closed and requires sign-in instead of issuing uncoordinated competing POSTs. Remote deployments therefore need HTTPS and supported browsers. [Web Locks documentation](https://developer.mozilla.org/en-US/docs/Web/API/Web_Locks_API).

Changes in `frontend/hooks/useAuth.tsx`: generation/mounted/session guards prevent stale bootstrap publication; identity-changing storage events recheck another tab's login/logout/tenant context; local login/logout invalidate pending bootstrap work. Ordinary same-session rotation does not trigger a competing bootstrap. `ProtectedRoute` owns the expiry redirect. Verbose user/error logging and the competing imperative expiry redirect were removed. Storage events reach other same-origin documents, so local login/logout still update their own context explicitly. [Storage-event documentation](https://developer.mozilla.org/en-US/docs/Web/API/Window/storage_event).

Five new component regressions reproduce timeout-after-rotation, stale bootstrap 401, stale bootstrap 200, plain network failure and missing Web Locks. They initially produced four failures before the implementation changes; all now pass. These tests use synthetic Axios transport and **are not real browser evidence**. C01 separately holds a successful response obtained from the real backend, changes identity through a second tab's real UI login, releases the unmodified old response, and verifies the first tab shows the current foreign fixture identity and receives cross-tab logout.

**Implementation-stage unresolved evidence, investigated in the independent audit above:** the first post-fix full run failed B02 at “stored successor”; both tabs had empty storage while the family remained unrevoked. [That failure](../../backend/checks/phase1-5-7914af1e3f6f4ff3bb94fd452900afae/browser-phase2a1-full.json) and the following seven successes remain preserved. Those successes alone did not close the gate. The subsequent audit captured the separate coordinator-first erasure, reproduced the missing receipt in three failing component cases, corrected it and reran the native browser matrix. The original failed run has no storage call stacks, so this is not a retrospective claim that every historical failure had one proven cause. Backend rotation/reuse rules were not weakened.

A reload of the refresh-issuing tab after a request is sent can lose the response. The durable attempt marker deliberately prevents replay and requires fresh login in that ambiguous case. The implementation-stage reload variant covered only the waiting tab; independent A05 now also executes issuer reload after real backend consumption. No browser clocks, JWT claims, password verification or authentication dependencies were mocked.
